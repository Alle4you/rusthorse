# 0010. A Debian package that installs and removes cleanly

- Status: Proposed
- Date: 2026-11-02

## Context

[ADR 0004](0004-native-distribution.md) chose native distribution: a
binary built with `cargo install`, "later also as `.deb`". Installing from
source takes a Rust toolchain, the GTK development packages and five manual
steps — `cargo install` three times, `chmod go-w` because of the umask of
Debian-based systems, copying the service file, linking the program where an
AI's shell finds it — and removing it takes as many, which the guide had
already got wrong once (it forgot `rusthorse-dialog`). Rusthorse should be as
easy to install and remove as any desktop application.

## Decision

Build a Debian package with [cargo-deb](https://github.com/kornelski/cargo-deb)
(`packaging/build-deb.sh`, described in `[package.metadata.deb]` of
`Cargo.toml`). One package, `rusthorse`, contains:

| Path | What |
|---|---|
| `/usr/bin/rusthorse`, `rusthorse-dialog`, `rusthorse-manager` | The programs, owned by root |
| `/usr/lib/systemd/user/rusthorse-agent.service` | The agent's user service |
| `/usr/share/applications/`, `/usr/share/icons/hicolor/` | The manager's menu entry and icon |
| `/usr/share/{bash-completion,zsh,fish}/…` | Shell completions, generated by the packaged program |
| `/usr/share/doc/rusthorse/` | README, changelog, security policy and `docs/` |

1. **The service is enabled for every user** on installation, as debhelper's
   `dh_installsystemduser` does (`deb-systemd-helper --user`): it starts at
   each login. Until the next login it is started with `systemctl --user
   start rusthorse-agent`. An upgrade keeps what the administrator chose; a
   user who does not want it masks it (`systemctl --user mask
   rusthorse-agent`). An agent without a vault does nothing until one is
   created.
2. **Upgrades do not restart running agents.** A restart locks the vault and
   stops every command the agent started — an AI's build, a deployment — at
   a moment nobody chose. The agent that keeps running uses the program it
   started with; `rusthorse doctor` says it has been replaced, and the next
   login or `systemctl --user restart rusthorse-agent` starts the new one.
3. **Removal stops the agents** of the users who are logged in (`systemctl
   --user --machine=USER@ stop`), so that no agent keeps running a program
   that is no longer installed. That locks their vaults.
4. **Removal never deletes data.** Vaults and audit logs live in users' home
   directories, where no package touches anything; the guide gives the
   command that deletes them. `apt remove` keeps the record of whether the
   service is enabled, as for any package; `apt purge` deletes it.
5. **The packaged service file differs from `contrib/systemd/`'s only in its
   program path** (`/usr/bin` instead of `%h/.cargo/bin`) and its comments;
   a test compares them. Both now let systemd create the socket's directory
   (`RuntimeDirectory=rusthorse`, mode `0700`) and remove it when the agent
   stops, so that stopping leaves no socket behind.
6. **Build on the oldest supported release.** The dependencies are computed
   from the libraries the programs were linked against (`dpkg-shlibdeps`):
   built on Ubuntu 24.04, the package installs on Ubuntu 24.04, Linux
   Mint 22 and Debian 13 or later.

## Alternatives considered

- **Binaries and `install.sh` / `uninstall.sh` in `~/.local`.** No root and
  any distribution, but no updates through apt, and programs in your home
  directory can be replaced by any process of yours. Kept for later, for
  other distributions, with signed checksums.
- **A `rusthorse setup` command that installs the service.** One step after
  downloading a binary; worth having with the previous option, not instead
  of a package.
- **AppImage.** It runs from a different temporary mount each time, which
  breaks the service's fixed program path and the rule that
  `rusthorse-dialog` sits next to the agent.
- **Restart agents on upgrade.** Rejected above (2).
- **Disable the service on `apt remove`.** Debian keeps that choice until
  purge, and users expect the same of every package.
- **Separate packages for the command-line program and the desktop
  programs.** A server could then skip GTK. Not needed yet; the agent falls
  back to zenity, and a split can come later without breaking anything.

## Consequences

- Installing is one command or a double click; removing is one command and
  leaves only the user's data.
- Root-owned programs cannot be replaced by the user's own processes. This
  does not change the threat model (L1): a process of the user can still
  put a service file of its own in `~/.config/systemd/user/`, which takes
  precedence.
- A service file left in `~/.config/systemd/user/` by an earlier `cargo`
  installation also takes precedence over the package's: the guide says to
  remove the source installation first.
- Until a release is published, the package is built from a clone.
