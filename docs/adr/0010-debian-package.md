## Context

[ADR 0004](0004-native-distribution.md) chose native distribution: a
binary built with `cargo install`, "later also as `.deb`". Installing from
source takes a Rust toolchain, the GTK development packages and five manual
steps — `cargo install` three times, `chmod go-w` because of the umask of
Debian-based systems, copying the service file, linking the program where an
AI's shell finds it — and removing it takes as many, which the guide had
already got wrong once (it forgot `rusthorse-dialog`). Rusthorse should be as
easy to install and remove as any desktop application.

## Decision

Build a Debian package with [cargo-deb](https://github.com/kornelski/cargo-deb)
(`packaging/build-deb.sh`, described in `[package.metadata.deb]` of
`Cargo.toml`). One package, `rusthorse`, contains:

| Path | What |
|---|---|
| `/usr/bin/rusthorse`, `rusthorse-dialog`, `rusthorse-manager`, `rusthorse-broker` | The programs, owned by root |
| `/usr/lib/systemd/user/rusthorse-agent.service` | The agent's user service |
| `/usr/share/applications/`, `/usr/share/icons/hicolor/` | The manager's menu entry and icon |
| `/usr/share/{bash-completion,zsh,fish}/…` | Shell completions, generated by the packaged program |
| `/usr/share/doc/rusthorse/` | README, changelogs, security policy, contributing guide, license and `docs/`; `copyright` |

1. **The service is enabled for every user** on installation, as debhelper's
   `dh_installsystemduser` does (`deb-systemd-helper --user`): it starts at
   each login. Until the next login it is started with `systemctl --user
   start rusthorse-agent`. An upgrade keeps what the administrator chose; a
   user who does not want it masks it (`systemctl --user mask
   rusthorse-agent`). An agent without a vault does nothing until one is
   created.
2. **Upgrades do not restart running agents.** A restart locks the vault and
   stops every command the agent started — an AI's build, a deployment — at
   a moment nobody chose. The agent that keeps running uses the program it
   started with; `rusthorse doctor` says it has been replaced, and the next
   login or `systemctl --user restart rusthorse-agent` starts the new one.
3. **Removal stops the agents** of the users who are logged in (`systemctl
   --user --machine=USER@ stop`), so that no agent keeps running a program
   that is no longer installed. That locks their vaults. It is an attempt:
   when the users cannot be listed, a session does not answer or an agent
   does not stop, a warning on standard error says so and what to do. When
   dpkg works on another root directory (`DPKG_ROOT`, for a system image),
   nothing is stopped: this computer's sessions are not that installation's.
4. **Removal never deletes data.** Vaults and audit logs live in users' home
   directories, where no package touches anything; the guide gives the
   command that deletes them. `apt remove` keeps the record of whether the
   service is enabled, as for any package; `apt purge` deletes it.
5. **The packaged service file differs from `contrib/systemd/`'s only in its
   program path** (`/usr/bin` instead of `%h/.cargo/bin`) and its comments;
   a test compares them. Both now let systemd create the socket's directory
   (`RuntimeDirectory=rusthorse`, mode `0700`) and remove it when the agent
   stops, so that stopping leaves no socket behind.
6. **The copyright file names every crate compiled in.** The programs contain
   195 Rust crates at the phase 1 dependency lock; their licenses (MIT, BSD,
   Apache-2.0, …) require their notices to go with the binaries.
   `packaging/copyright.py` lists each crate that Cargo.lock resolves for the
   four programs — version, license, source and copyright notices — followed
   by the license texts the crates ship, each text once. A crate whose package
   ships no license file is listed in the script's exceptions, checked by
   hand: its license file from the upstream revision it was published from is
   kept in `packaging/licenses/`, or the crate is shown to contain no code. A
   notice is never made up from the `authors` field, and any other such crate
   stops the build. The installed documentation is copied by
   `packaging/docs.py`, which points links to files the package does not
   install (the source code) to GitHub at the revision built, and fails on any
   link that leads nowhere. (Stated exactly on 2026-11-09: it fails on a
   relative Markdown link, outside code fences, whose file or directory is not
   in the repository; it checks neither anchors nor links to other sites.) A
   Debian changelog (`changelog.Debian.gz`) records
   the packaging. The broker adds ring's nested licence texts and source
   notices, including Portions Copyright lines. `copyright.py` checks nested
   files by crate/version and verifies exclusions against the enabled
   features.
7. **Build on the oldest supported release.** The dependencies are computed
   from the libraries the programs were linked against (`dpkg-shlibdeps`):
   built on Ubuntu 24.04, the package installs on Ubuntu 24.04, Linux
   Mint 22 and Debian 13 or later.

8. **The broker needs the system CA file.** The package recommends
   `ca-certificates`; without a usable root-owned bundle, broker runs fail
   closed while the other features still work. See ADR 0013 for the file
   checks and HTTP scope.
9. **Check what ships before it ships.** `build-deb.sh` checks the built
   broker, generates assets and runs cargo-deb, which never writes where
   `--output` points: the script takes `--output DIR` itself, in each form
   cargo-deb reads (default `target/debian`; a DIR given that exists and is
   not a directory is refused before anything is built), and gives cargo-deb
   a new staging directory of its own, which only its user can enter. There
   `check-broker.py` lists what cargo-deb wrote (it does not parse
   cargo-deb's output, so a name is handled whole whatever it holds): each
   entry must be a regular file, examined without being followed or opened,
   and there must be at least one. It extracts each and checks every
   packaged `rusthorse-broker` (at least one across the run). Only if all
   pass are the packages moved to DIR, created if missing, under the names
   cargo-deb gave them: renamed on the same file system, otherwise copied into
   a new file created in DIR, flushed and renamed. A symbolic or hard link
   already at such a name is replaced, never followed or written through. If
   a package is refused, or anything else stops the check, the staging
   directory is deleted whole (symbolic links in it are not followed) and
   nothing reaches DIR; a move that fails leaves there only the packages
   moved before it, which passed. The script also deletes the staging
   directory when cargo-deb fails or the script is interrupted; a run killed
   outright leaves it to the next run. Outside `target/release/packaging`,
   which it makes again on each run, the script removes only what a package
   that passed replaces at its name in DIR and the new file of a copy that
   fails; cargo-deb itself, whatever `--output` says, deletes the packages of
   rusthorse that it finds in `target/debian` before it writes. The script
   refuses test-feature builds, alternate targets, another manifest
   (`--manifest-path`: cargo-deb puts the package name of the manifest,
   unchecked, in each package's file name, so a `/` in it would write the
   package outside the staging directory) and install-before-check options.
   This replaced the cleanup of refused packages, which Q01 had extended to
   any name (R01–R04 in the review history). No feature for tests belongs in
   a release.

## Alternatives considered

- **Binaries and `install.sh` / `uninstall.sh` in `~/.local`.** No root and
  any distribution, but no updates through apt, and programs in your home
  directory can be replaced by any process of yours. Kept for later, for
  other distributions, with signed checksums.
- **A `rusthorse setup` command that installs the service.** One step after
  downloading a binary; worth having with the previous option, not instead
  of a package.
- **AppImage.** It runs from a different temporary mount each time, which
  breaks the service's fixed program path and the rule that
  `rusthorse-dialog` sits next to the agent.
- **Restart agents on upgrade.** Rejected above (2).
- **Disable the service on `apt remove`.** Debian keeps that choice until
  purge, and users expect the same of every package.
- **Separate packages for the command-line program and the desktop
  programs.** A server could then skip GTK. Not needed yet; the agent falls
  back to zenity, and a split can come later without breaking anything.

## Consequences

- Installing is one command or a double click; removing is one command and
  leaves only the user's data.
- Root-owned programs cannot be replaced by the user's own processes. This
  does not change the threat model (L1): a process of the user can still
  put a service file of its own in `~/.config/systemd/user/`, which takes
  precedence.
- A service file left in `~/.config/systemd/user/` by an earlier `cargo`
  installation also takes precedence over the package's: the guide says to
  remove the source installation first.
- Until a release is published, the package is built from a clone, and
  only with `packaging/build-deb.sh` (plain `cargo deb` lacks the generated
  files).
- After an upgrade that changes the service file, each user's systemd
  needs `systemctl --user daemon-reload` before a restart picks it up; the
  guide says so.
- No manual pages yet (planned, generated from the command-line
  definition).
